## How it works

Sixteen RC servos, one serial port, one chip.

The design is three blocks that you can lift out and reuse separately:

```
        ui[1] ──► ┌──────────┐  addr/data  ┌──────────────┐  16 x 8 bit  ┌────────┐ ──► uo[7:1]  ch0..ch6
   uart_rx        │ uart_if  │ ──────────► │ rb_pwm16     │ ───────────► │ pwm16  │ ──► uio[7:0] ch7..ch14
        uo[0] ◄── │ protocol │ ◄────────── │ register bank│              │ engine │ ──► uo[0]    ch15*
   uart_tx        └──────────┘             └──────────────┘              └────────┘
```

**`uart_if`** is a 115200 8N1 UART wrapped around a four command register
protocol - the same one the `fpga_template` and `ucom` tools have always
spoken, so every existing script keeps working:

| Operation    | On the wire                            | Answer            |
|--------------|----------------------------------------|-------------------|
| Single write | `'W' + addr + data`                    | none              |
| Single read  | `'R' + addr`                           | `data`            |
| Block write  | `'B' + addr + len + data0 + data1 ...` | none              |
| Block read   | `'b' + addr + len`                     | `data0 + data1 …` |

**`rb_pwm16`** is generated from `regmap/register_bank.go`, which also emits the
register file that `ucom` reads, the JSON, and the table below. One source of
truth for hardware, software and documentation.

**`pwm16`** is where the area went, and where the trick is. A servo needs a
20 ms frame with a 1.0-2.0 ms pulse. Doing that sixteen times over would mean
sixteen 13 bit counters. Instead there is **one** shared timebase and sixteen
8 bit comparators:

```
          |<───────────────────── 20 ms frame ─────────────────────>|
          |<── 1 ms ──>|<── 0..1 ms ──>|                            |
           ____________________________
 ch[n] ___|                            |____________________________
           always high    position       always low
```

A prescaler produces one *tick* every `clk_div_pwm` clocks, aimed at
1 ms / 256 = 3.90625 µs. The frame counter runs 0…5119 ticks = 20 ms. During
the first 256 ticks every enabled channel is high; during the next 256 it stays
high while `frame_counter[7:0] < position`. So

| `pwm.chN` | pulse    | servo         |
|-----------|----------|---------------|
| `0x00`    | 1.000 ms | one end stop  |
| `0x80`    | 1.500 ms | centre        |
| `0xFF`    | 1.996 ms | other end stop|

5120 is exactly 20 × 256, so the low byte of the frame counter also gives a
clean 256 tick period for **plain PWM mode** (`ctrl.servo_mode = 0`), where the
same registers mean duty / 256 at roughly 1 kHz - handy for LEDs and motors.

### Clocking

Both dividers are registers, and both fall back to a built in default when left
at zero, selected by the `ui[2]` strap. So the chip answers at 115200 baud out
of reset without anyone having programmed anything:

| `ui[2]` | clock  | UART divider | PWM divider | tick    |
|---------|--------|--------------|-------------|---------|
| 0       | 10 MHz | 87           | 39          | 3.90 µs |
| 1       | 50 MHz | 434          | 195         | 3.90 µs |

Writing a non zero `ctrl.clk_div_com` / `ctrl.clk_div_pwm` overrides the
default, so any other clock rate works too.

### Getting all sixteen channels out of sixteen pins

There are 16 usable output pins and the UART needs one of them. Channels 0-14
have a pin each; channel 15 shares `uo[0]` with the UART transmitter and takes
over when you clear `ctrl.uart_tx_en` - at which point you can still write
registers, you just cannot read them back any more.

### If nobody has written any software yet

Strap `ui[0]` high and the chip runs its own slow triangle sweep across all
sixteen channels, odd channels mirroring the even ones. No host, no driver, no
UART. A rising edge on `ui[3]` reloads every channel with `0x80`, which is the
mechanical panic button.

## How to test

Set the demo board clock to **10 MHz** (or 50 MHz with `ui[2]` strapped high)
and connect a 115200 8N1 serial port to `ui[1]` / `uo[0]`.

`ui[1]` RX / `uo[0]` TX is [option 2 of the Tiny Tapeout recommended UART
pinout](https://tinytapeout.com/specs/pinouts/), so on the demo board the
RP2040 bridges the link to the board's USB-C connector - no adapter, no wiring.

**No software at all:** strap `ui[0]` high. Every channel starts sweeping.
That alone proves the clock, the reset, the timebase and all sixteen output
pins.

**With [`ucom`](https://github.com/jorgenkraghjakobsen/ucom):**

```bash
cd sw
ucom r ctrl.chip_id          # -> 0x16, the link works
ucom w pwm.ch3 0xC0          # channel 3 to about 1.75 ms
ucom r 0x10 16               # block read all sixteen positions
ucom w ctrl.center_all 1     # everything back to 1.5 ms
./bringup.sh                 # the whole pass/fail sequence
```

**With the web UI:** `cd sw/pwmui && go run .` and open
<http://localhost:8080> for sixteen sliders with a live microsecond readout.

**On a scope,** with everything at reset, `uo[1]` should show a 1.5 ms pulse
every 20 ms.

## External hardware

- Any 115200 8N1 serial port on `ui[1]` / `uo[0]` - the RP2040 on the TT demo
  board bridges this pair to USB by itself, or use any USB-serial adapter.
- Up to 15 hobby RC servos (SG90 and friends). **Power the servos from their
  own 5 V supply**, not from the demo board, and tie the grounds together. The
  chip only drives the signal wire.
- Nothing at all is also fine: strap `ui[0]` high and watch the pins on a
  scope or a logic analyser.
